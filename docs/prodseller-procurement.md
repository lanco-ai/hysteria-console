# ProdSeller 管理员采购预订

管理员使用自己的供应商余额，一次预订采购指定商品和数量。草稿不下单；明确启用后才开始监控。等待库存足以一次交付全部数量，成功后停止，不做长期自动补货，不向顾客扣款。

页面入口是商品后台侧栏的「采购预订」（`/admin/shop?view=procurement`），与商品管理同属一个页面组件，切换时未保存的商品修改不会丢失。宽屏左侧是余额与新建预订，右侧是预订记录；窄屏上下排列。交付内容只在管理员主动点击后返回，不进入列表、公开目录或日志。

## 报价

- 概览接口不联系供应商：商品价格取自目录刷新时缓存的 ProdSeller 报价，缺货商品同样有价格，库存只知道有货或缺货。缓存里的成本按固定汇率换成人民币，除回汇率即得美元报价。
- 「刷新余额和报价」除余额外，再以 GET 读取两件商品的实时单价和库存数。实时报价只保存在服务进程内存中，不写入 procurement.json，旧版本仍能读取该文件。
- 页面可以把现价填入触发单价，并按数量计算条件金额；超过当前余额时提示启用后会因余额不足暂停。

## 资金与异常处理

- 供应商 API 仅支持提交前检查价格，不支持锁价或原子最高金额约束。触发单价是提交条件，不能保证供应商检查后调价时的最终扣款。启用时必须再次确认这一点及预估金额。
- 每份预订单固定一个幂等键；持久化「提交中」并 fsync 后才发送唯一一次下单请求。
- 网络超时、响应损坏、进程中断或保存结果失败均不自动重试下单；记录为待核实，提示管理员到供应商核对。已取得订单号的情况只允许 GET 查询交付状态。
- 暂停、取消、到期、来源关闭/删除后不创建新订单。删除后重新添加来源也不会恢复旧任务。已扣款订单不能通过取消预订退款。
- 多线程/进程通过文件锁串行执行。下单阶段同时持有商品来源设置锁，使停用来源与下单有明确先后关系。
- 状态独立存于 state/shop/procurement.json（0600）。回滚不删除此文件；恢复旧备份时应保持采购调度关闭并核对供应商订单，不能恢复旧的待购状态后直接运行。

## 验证

所有采购测试使用 HTTP 模拟回复；不调用真实 POST /v1/orders。覆盖草稿、权限与 CSRF、重入、故障恢复、过期、来源删除重加、价格/余额/库存检查、机密遮蔽及手机布局。上线不创建真实预订。
